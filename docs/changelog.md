## [Unreleased]

### Added

- **Відмітка прибуття й неявки доступна без відкриття картки запису.** У списку календаря реєстратор і адміністратор можуть поставити «Прийшов» або «Не прийшов» прямо в рядку; кнопки зʼявляються лише для дозволених переходів і блокуються під час збереження. Повна картка запису лишається доступною окремою кнопкою.

### Fixed

- **Стандартний lint не аналізує згенеровані bundles локального runtime.** До ESLint ignores додано лише `.wrangler/**` і `.sites-runtime/**`; після запусків локального Worker звичайний `npm run lint` знову проходить із 0 errors / 40 baseline warnings без додаткових CLI-виключень. Вихідний код і тести залишаються під перевіркою.

- **Командна панель staff більше не розтягує мобільну сторінку.** Глобальний `nav { display:flex }` розташовував два рівні бізнес-навігації поруч; для `.workspaceBusinessBar` задано явне вертикальне компонування. На локальному Worker перевірено протоколи, календар, видачу й задачі при 1440/768/390 px: 12/12 перевірок без горизонтального переповнення сторінки, посилання панелі доступні з клавіатури. Схема, ролі та дані не змінені.

- **Видача підписаного результату в D1 більше не повертає помилковий конфлікт після успішної дії.** Авторизований локальний браузерний прогін виявив HTTP 409 після фактичної видачі: `meta.changes` включає записи тригерів. Видача протоколу й addendum тепер підтверджує точний умовний перехід через `UPDATE … RETURNING`; перевірки ролі, tenant, версії та документа-реєстратора збережено. Додано regression-тест із trigger-inclusive метаданими. Повний локальний маршрут і окрема видача addendum пройшли на синтетичній D1; 1555/1555 тестів успішні. Production/staging deploy не виконувався.

### Added

- **Швидкі дії прибуття й неявки з календаря.** У панелі запису можна позначити «Прийшов» або «Не прийшов», якщо такий перехід дозволяє наявна модель станів. Доступ лише адміністратору й реєстратору; запис проходить через чинний API та журнал подій.


- **Підрахунок і фільтр очікуваних описів із попередніх днів.** У черзі протоколів окремо видно виконані дослідження, які ще чекають опису з попередніх днів; натискання фільтрує їх у вже доступній tenant/role-скоупованій черзі. Без нової SLA-вимоги, схеми чи API.

- **Перехід із заявки до відповідного дня календаря.** У картці активної заявки на дошці прийому є пряме посилання на день її запланованої дати в календарі записів. Посилання лише відкриває календар і не змінює слот чи статус.

- **Follow-up задача з картки пацієнта з відповідальним і строком.** Із конкретного запису можна створити задачу `/staff/tasks` із прив’язкою до booking: за замовчуванням відповідальний — автор, строк — сьогодні; обидва значення редагуються перед збереженням і обов’язкові саме для цього типу задачі. API перевіряє роль, tenant і доступ призначеного працівника до дослідження. ПІБ і медичний текст у задачу не копіюються; використовується наявна таблиця.

- **OTP для протоколів у кабінеті пацієнта.** Вхід за телефоном і датою народження лишається для перевірки записів; `/api/my-protocol` тепер вимагає сесію після підтвердження одноразового коду. Рівень сесії зберігається у `patient_sessions.auth_method` (міграція `0129_patient_protocol_otp.sql`, старі сесії безпечно вважаються `knowledge`). Інтерфейс кабінету пропонує підтвердити номер перед відкриттям протоколу. Тести проходять OTP API на синтетичній D1 без реальної доставки повідомлень.

- **Надійність Telegram webhook при недоступній базі.** Якщо D1-біндинг відсутній, `/api/telegram/webhook` повертає `503 Service Unavailable` замість `200 OK`, щоб Telegram не вважав update обробленим і повторив доставку. Додано behavior-тест. Зовнішні повідомлення не надсилалися.

- **Постійний план роботи для AI-агентів.** AGENTS.md тепер вимагає на початку кожної сесії звіряти main, PR/Actions і docs/quality-audit.md; оновлювати застарілий статус, обирати один незакритий пріоритет, перевіряти прогрес за планом після кожної фази й фіксувати наступний крок. Також розмежовано CI, production deploy та живий staging.

- **Автоматична задача після неявки.** Коли запис має статус `no_show`, система створює ідемпотентну задачу у спільній черзі реєстратури «Зв'язатися щодо повторного запису» без ПІБ і телефону; повторний запуск не дублює задачу, а її виконання лишається виконаним, доки статус запису не зміниться. Задачу й картку бачать адміністратори та реєстратори; обидві ролі можуть її закрити.
- **Автозбереження чернетки протоколу в редакторі `/staff/protocols`.** Чернетка тепер зберігається автоматично ~1с після завершення введення (debounce) через **наявний** `PUT /api/staff/protocols` — без паралельного API. Нова чиста логіка рішень у `lib/protocol-autosave.ts` (`shouldAutosave`, `remainsDirtyAfterSave`, `isVersionConflict`, `autosaveLabel`, `AUTOSAVE_DELAY_MS`). Гарантії: не зберігає при первинному завантаженні/гідрації чи без реальних змін (гейт за `dirty` + лічильник правок `editSeq`); не створює зайвих ревізій для незміненого вмісту; `baseVersion` оновлюється з відповіді сервера; автозбереження **лише для `draft`** — `signed`/`issued` ніколи не автозберігаються (серверні гейти не послаблено); спільний in-flight guard (`saveInFlight`) не дає дублювати запит між автозбереженням і явною кнопкою «Зберегти чернетку». Індикатор станів українською: «Є незбережені зміни» / «Збереження…» / «Збережено» / помилка. При **конфлікті версій** (409 optimistic lock) серверні дані не перезаписуються мовчки: введений текст лишається у формі, показано блок відновлення з діями «Копіювати мій текст» і «Оновити серверну версію». Медичний текст не потрапляє в `localStorage`/`sessionStorage`, логи, аналітику чи URL. Ролі, tenant-ізоляція та статусна модель не змінювались. Додано `tests/protocol-autosave.behavior.test.mjs` (11: debounce-гейт, заборона для signed/issued, відсутність зайвих збережень, конфлікт версій у реальному D1 зі збереженням новішого тексту, проводка редактора).

### Changed

- **Сторінку продажу `/product` прибрано з публічного контуру.** Власник підтвердив, що RadiologyOS наразі створюється для внутрішньої роботи рентгенвідділення, а не для продажу. Видалено маршрут та його окремі marketing-only перевірки й стилі. Корисний workflow-first підхід уже живе у внутрішньому `/staff/dashboard` (#690): швидкі входи ведуть у наявні черги й робочі дії, без другого дубльованого інтерфейсу. Публічна вітрина пацієнтів і клінічні сторінки лишаються окремим каналом запису.

- **CTA на `/product` ведуть у WhatsApp.** Кнопки загального контакту, аудиторій і тарифів тепер відкривають готове повідомлення; обіцянки про 14-денний trial, самореєстрацію, оплату після реєстрації, річну знижку й скасування прибрано, бо відповідного self-service процесу немає. Ціни на сторінці не змінювались. Додано source-inspection тести для адресатів CTA й відсутності застарілих обіцянок.

- **Уточнено комерційні твердження `/product` за кодом.** Цифрові тарифи прибрано до підтвердження умов. Сторінку перебудовано за потоком «цінність → аудиторія → робочий процес → ролі/дані → доступність → ціна/FAQ», використавши 95sales CRM як структурний референс без копіювання бренду, текстів чи коду. Вона розрізняє внутрішній DICOM/PACS-модуль та XLSX-експорт для дозволених staff-ролей і їхню окремо не підтверджену доступність клієнтам; розрахунок зарплати в коді не знайдено, графік підтримки 24/7 кодом підтвердити неможливо. Калькулятор позначено оцінкою, без обіцянки ефекту від нагадувань. Додано регресійні тести маркетингових тверджень.

- **Read-only аудит WhatsApp webhook.** `docs/quality-audit.md` фіксує tenant-scoped secret, 503 при відсутній D1 і UNIQUE дедуплікацію повідомлень. Виявлено питання моделі identity: бот може показати перелік послуг і час записів за самим номером WhatsApp, тоді як доменна модель вимагає OTP або точний код заявки для patient self-service. Власник підтвердив вузьку видачу найближчої послуги й дати/часу за WhatsApp-номером; спільний номер означає спільну видимість цих записів, OTP для кабінету лишається.

- **Звірено матрицю якості з main станом на 2026-10-29.** Оновлено статуси `/staff/dashboard`, `/staff/intake`, `/staff/studies`, `/staff/protocols`, `/staff/tasks`, `/staff/patients` і `/staff/audit` за PR #686–#703; старий пріоритет `/staff/appointments` виправлено з урахуванням аудиту #643. Видалено застарілі приблизні підрахунки API й тестів, локальний browser-block позначено як історичне спостереження, наступним пріоритетом визначено per-route API inventory та read-only review.

- **Уточнено `docs/pilot-runbook.md` під staging-автоматизацію (три місця).** (1) §0 крок 4: ручне застосування міграцій позначено як **fallback** — звичайний шлях тепер через `staging.yml` (налаштувати Environment + запустити workflow). (2) §2 розділено на дві **окремо названі** репетиції відновлення — **2A** (export/import синтетичного дампа, ручна) і **2B** (D1 Time Travel на тимчасовій базі через `staging-restore-rehearsal.yml`); чекліст має окремі чекбокси 2A/2B, щоб звіт фіксував, яку саме пройдено. (3) Telegram: явно розмежовано, що автоматизований E2E з тестовим секретом перевіряє лише **обробку вебхука** (не доставку), а ручний тестовий бот (§4Б) — саме **зовнішню інтеграцію** через Bot API; чекліст розділено на Б1 (обробка) і Б2 (доставка). Лише документація.

### Added

- **Staging preflight: автоматична звірка, що staging ≠ production (`scripts/staging-preflight.mjs`).** У `staging.yml` додано крок **до будь-якого звернення до Cloudflare**, що прибирає ручну звірку: читає production D1 id / R2 bucket / hostname з `wrangler.cloudflare.toml` (не захардкоджено, безпечно до ротації), нормалізує hostname (регістр/схема/шлях/порт/крапка) і звіряє зі staging-змінними. **Fail-closed**: падає при збігу з production, при відсутніх чи плейсхолдерних staging-значеннях, якщо не може прочитати конфіг або визначити production-значення. Креденшели не читаються й не виводяться. Додано `tests/staging-preflight.test.mjs` (10: безпечні значення; збіги D1/bucket/hostname; різний регістр/схема/слеш hostname; інший піддомен — ок; відсутнє значення; плейсхолдер; нечитабельний конфіг; невизначуване production-значення; відсутність витоку креденшелів) + перевірка в `staging-workflows.test.mjs`, що preflight передує рендеру й усім Cloudflare-викликам.
- **Автоматизація staging через GitHub Actions (production workflow не змінено).** Три workflow-и: (1) `ci.yml` розширено — на кожен PR/push, окрім наявних перевірок, застосовує **всі** D1-міграції до свіжої локальної синтетичної бази (новий `scripts/apply-d1-migrations-local.mjs`: 128 міграцій + синтетичний запис пацієнта/дослідження, без мережі/Cloudflare), і зберігає SHA релізу та звіт міграцій як summary+артефакт; (2) новий `staging.yml` (push у `main` + ручний) — рендерить `wrangler.staging.toml` з `wrangler.staging.example.toml` + значень GitHub Environment `staging` (реальні id/секрети не комітяться), застосовує міграції до staging через спільний fail-closed виконавець, деплоїть **лише** з `wrangler.staging.toml`, робить health check розгорнутого staging і безпечний in-process E2E (пацієнт→дослідження→опис, ролі, ізоляція організацій, Telegram через тестовий секрет вебхука — mock/test adapter, без реальних повідомлень), summary+артефакт; інертний, доки `vars.STAGING_ENABLED != 'true'`; (3) новий `staging-restore-rehearsal.yml` (лише ручний, підтвердження `REHEARSE`) — створює **тимчасову** D1, репетирує Time Travel restore на синтетиці, перевіряє цільову базу, **ніколи** не приймає продакшн `database_id`, і **завжди** (`always()`) видаляє лише створену ним базу. Cloudflare-креденшели — лише з Environment secrets; production `deploy.yml` не змінювався й цими workflow-ами не запускається. Список потрібних vars/secrets — у `docs/pilot-runbook.md` §0b. Додано `tests/staging-workflows.test.mjs` (8, парсинг YAML + інваріанти безпеки).
- **Runbook обмеженого пілоту + шаблон staging-конфігу.** `docs/pilot-runbook.md` — короткий операційний runbook, що доповнює `docs/production-smoke-checklist.md` і `HOSTING.md`: перевірка версії та застосованих міграцій (`d1_migrations` vs `drizzle/*.sql`, перевірка схеми без читання рядків пацієнтів), резервне копіювання (D1 Time Travel bookmark) і репетиція відновлення на staging **лише синтетичними даними**, перевірка авторизації та ізоляції організацій (серверна RBAC, два синтетичні org A/B), основні сценарії (пацієнт→дослідження→опис→підписання/видача + Telegram-заявка з чесним статусом), виявлення помилок після деплою (`wrangler tail`, `/api/staff/system/health`, смоук-чек) і процедура відкату (known-good SHA + D1 Time Travel). Явне застереження: **без заяв про регуляторну відповідність** без окремої перевірки; на staging не переносити реальні дані й не надсилати реальних повідомлень; наприкінці — ручний чекліст пілоту. Додано шаблон **`wrangler.staging.example.toml`** (плейсхолдери `REPLACE_WITH_STAGING_D1_ID`/R2/hostname — продакшн `database_id` і домен навмисно **не** скопійовані; staging-ресурс і секрети налаштовує команда у своєму Cloudflare-акаунті) і **fail-closed захист** у спільному виконавці міграцій `scripts/apply-d1-migrations-remote.sh`: міграція/деплой зупиняється з явним повідомленням (до будь-якого звернення до D1), якщо (а) `database_id` лишився плейсхолдером (прод або staging), (б) обрана база (1-й аргумент) не збігається з `database_name` у конфігу, або (в) **не**-продакшн конфіг указує на **продакшн** `database_id` — прод-ID зчитується з `wrangler.cloudflare.toml`, не захардкоджений, тож ротація безпечна. Додано `tests/staging-config-template.test.mjs` (8).
- **Прямі входи робочого процесу на дашборді + людська мітка аудиту `protocol_signed` (F/E).** На «Пульт відділення» (`/staff/dashboard`) додано рядок прямих входів із підписами **«Нове дослідження», «Черга описів», «На перевірці», «Видано», «Заявки»** — закриває 🟡 з фінального огляду (п'ять іменованих точок входу). Додано `tests/dashboard-workflow-entries.behavior.test.mjs` (6: наявність і підписи входів, коректні маршрути, обробка `?queue=`/`?new=`, збережений гейт `canCreateStudy`, адаптив+темна тема, мітка аудиту + емісія події).
- **Структуровані параметри дослідження: анатомічна ділянка (кілька) + метод контрастування (A, міграція `0128`).** Дослідження (`bookings`) тепер має два структуровані поля замість лише лічильника ділянок/вільного тексту: `anatomical_regions` (кома-ключі, **кілька** ділянок) і `contrast_method`. Сумісна, **неруйнівна** зміна — `ADD COLUMN` з дефолтом `''` («не вказано»), наявні дослідження не чіпаються; невідоме/незаповнене лишається **явно невказаним** (`''`), а не вигаданим значенням. ### Security

- **`sharp` (під `next`) закріплено на `0.35.5`** — закрито HIGH-вразливість у залежності `librsvg` (CVE-2026-96889, GHSA-wq5f-xc86-pv6w, зачеплені `sharp < 0.35.5`). Прод-шлях — `next → sharp`; CI-гейт `npm audit --omit=dev --audit-level=high` почав падати на цій новорозкритій advisory, знову блокуючи всі PR. Оновлено наявний nested-override `next.sharp` `0.35.4 → 0.35.5`; після бампу `audit --audit-level=high` — чистий. Верхньорівневий `sharp` лишається dev-залежністю (поза `--omit=dev`). Лише lock + `overrides`; код не змінено.
- **`source-map-js` закріплено на `1.2.2`** (через `overrides`) — закрито HIGH-вразливість event-loop DoS через індексовані offset-и секцій source-map (GHSA-68fv-2mgg-jv7q, зачеплені 1.0.0–1.2.1). Пакет приходить транзитивно (`next` → `postcss@8.5.25` → `source-map-js`); CI-гейт `npm audit --omit=dev --audit-level=high` почав падати на цій новорозкритій advisory, знову блокуючи всі PR. `1.2.2` задовольняє `postcss ^1.0.0`, тож бамп безпечний; після нього `audit --audit-level=high` — чистий (лишилась одна moderate `baseline-browser-mapping`, нижче гейту). Лише lock-файл + `overrides`; код не змінено.
- **Next.js `16.3.5` → `16.3.8`** — закрито критичну вразливість RCE у `next/og` `ImageResponse` (GHSA-vcvr-r3jv-pc5j, зачеплені 16.2.0–16.3.5). CI-гейт `npm audit --omit=dev --audit-level=high` (у `ci.yml` і `deploy.yml`) почав падати на цій новорозкритій advisory, блокуючи всі PR. Проєкт не використовує `next/og`/`ImageResponse`, тож RCE недосяжний, але прод-залежність усе одно оновлено до пропатченої версії в межах того ж мінора. `vinext` (Vite-фреймворк) не залежить від `next`, тож бамп безпечний; оновлено лише `next` у lock-файлі, збірка/тести без змін.

- DICOM/PACS-зв'язки отримали фізичний tenant-захист у D1: imaging study не може посилатися на заявку іншої організації, а один непорожній `StudyInstanceUID` не може бути прив'язаний до двох заявок одного tenant.
- Drizzle schema синхронізовано з tenant/UID-індексами `imaging_studies`; додано D1 behavioral tests і перевірку належності PACS settings існуючій організації.
- Автоматична DICOM-прив'язка за Accession тепер додатково вимагає валідний StudyInstanceUID, збіг модальності та дати дослідження; невідповідність fail-closed і не змінює imaging link.
- QIDO series parser відкидає некоректні `SeriesInstanceUID`; відмови auto-link аудіюються без UID/ПІБ/телефону та покриті behavioral tests.
- Patient OTP/session тепер несуть доведену identity scope (`dob` або точний `booking`), тому спільний сімейний номер телефону не розширює доступ до чужих заявок, протоколів, скасування чи оплати; D1 фізично перевіряє scope за реальною заявкою.
- Telegram deep-link і chat binding також стали identity-scoped. Небезпечні legacy phone-wide patient sessions, link tokens і Telegram chat bindings інвалідовуються під час міграції замість автоматичного перенесення між членами сім'ї.
- Додано behavioral regression coverage для двох пацієнтів з одним телефоном та різними датами народження.
- Історія `protocol_revisions` стала фізично append-only у D1: існуючу клінічну версію не можна UPDATE/DELETE; виправлення створює нову версію.
- Додано окремий read-only endpoint конкретної ревізії з tenant/RBAC/assignment перевіркою та security audit без клінічного тексту, плюс behavioral coverage незмінності та міжтенантної ізоляції.
