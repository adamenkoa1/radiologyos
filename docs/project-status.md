# RadiologyOS — статус проєкту (підсумкова довідка)

Єдина стисла довідка про стан проєкту, щоб відновлювати роботу **без переграшу
всієї історії сесій** (економія контексту/токенів). Канонічні деталі змін — у
`docs/changelog.md`; обов'язкові правила — `AGENTS.md` і `CLAUDE.md`. Якщо цей
файл розходиться з `changelog.md`, істина — у `changelog.md`.

> Оновлюйте цей файл лише коротко, коли завершено помітний етап. Деталі — у
> changelog, не тут.

## Реалізовано і злито в `main` (за блоками майстер-промпту A–F)

- **A. Реальні пацієнти та дослідження.** CRUD картки пацієнта з персистенцією в
  D1 (без localStorage для медданих), поле **статі**, walk-in і планове
  створення дослідження, дедуплікація за телефоном, **структуровані анатомічна
  ділянка (кілька) + метод контрастування** (`lib/study-attributes.ts`).
- **B. Редактор опису.** Життєвий цикл `draft→ready→signed→issued` із серверними
  переходами та DB-immutability підписаного вмісту; структуровані шаблони/макроси
  + вільний текст; друк/PDF; історія ревізій; структуровані знахідки; порівняння
  з попереднім дослідженням. *(Автозбереження чернетки — відкритий PR, див. нижче.)*
- **C. Черга/воркфлоу.** Черга описів із пошуком і **фільтрами** (модальність /
  виконавець / діапазон дат); реєстр `/staff/studies`; дошка `/staff/board`;
  перевірка конфлікту слотів у записі.
- **D. Telegram-заявки.** Захоплення вхідних у вебхуку (ідемпотентно за
  `update_id`, fail-closed секрет) + **видима черга реєстратора** на
  `/staff/protocols`; конвертація в дослідження; **чесний статус** підтвердження;
  мінімум PII у чаті. Секрети — per-org у БД, не в коді.
- **E. Ролі/доступ/аудит.** Серверний RBAC (`lib/staff-auth.ts`); реєстратор не
  редагує підписаний протокол; аудит ключових подій із людськими українськими
  мітками (включно з `protocol_signed`); без заяв про регуляторну відповідність.
- **F. UI.** Прямі входи на дашборді («Нове дослідження», «Черга описів»,
  «На перевірці», «Видано», «Заявки»); українська; адаптив; темна тема.

## Інфраструктура пілоту та staging-автоматизація (злито)

- `docs/pilot-runbook.md` — runbook пілоту (версія/міграції, бекап/відновлення
  2A dump + 2B Time Travel, авторизація/ізоляція, сценарії, відкат, Telegram
  обробка vs доставка). §0b — одноразове налаштування staging.
- `wrangler.staging.example.toml` — шаблон (плейсхолдери, без продакшн-id/домену).
- Fail-closed guards: `scripts/apply-d1-migrations-remote.sh` (плейсхолдер /
  невідповідність бази / продакшн-id) + `scripts/staging-preflight.mjs`
  (staging ≠ production, нормалізація hostname, без витоку креденшелів).
- GitHub Actions: `ci.yml` (PR-перевірки + локальні синтетичні міграції),
  `staging.yml` (міграції→деплой лише з `wrangler.staging.toml`→health→E2E),
  `staging-restore-rehearsal.yml` (ручний, тимчасова база, always()-cleanup).
  **`STAGING_ENABLED` — repository-variable** (не environment), інакше job
  пропускається. **Production `deploy.yml` не змінювався.**

## Відкриті PR цієї роботи (на рев'ю власника; агент не зливає сам)

- **#701** — автозбереження чернетки протоколу (debounce + optimistic lock).

## Останній фактичний гейт (за командою, поза агент-сесією)

Перший **живий** staging-прогін виконує команда у своєму Cloudflare/GitHub:
Repository variable `STAGING_ENABLED=true`; Environment `staging` (vars
`STAGING_D1_DATABASE_ID`/`STAGING_R2_BUCKET`/`STAGING_HOSTNAME`; secrets
`CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID`); створені Cloudflare D1
`radiologyos-staging` + приватний R2 + домен → **Actions → Staging → Run**, тоді
restore rehearsal (`REHEARSE`). Деталі — `docs/pilot-runbook.md` §0b. Хмарна
агент-сесія не має Cloudflare-креденшелів і права `actions: write`, тож запускає
це не вона.

## Технічне

- Остання міграція на момент довідки — `drizzle/0129_*`. `npm run db:generate` —
  no-op guard; Drizzle-метадані rebaselined при кожній зміні схеми.
- Гейт доставки: `npx tsc --noEmit` → `npm run lint` (0 errors) → `npm test`.
- Один функціональний крок — один невеликий PR; після змін оновити
  `docs/changelog.md` (і цей файл за потреби).

## Як відновити роботу дешево (для наступної сесії)

1. Прочитати `AGENTS.md`, `CLAUDE.md`, цей файл і свіжий «Unreleased» у
   `docs/changelog.md` — цього достатньо для контексту, без перегляду всієї історії.
2. Прогнати гейт (tsc → lint → test), звіритися з відкритими PR вище.
3. Не чіпати production workflow/конфіг; staging — лише синтетичні дані.
