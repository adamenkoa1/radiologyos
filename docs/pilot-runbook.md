# RadiologyOS — runbook обмеженого пілоту

Операційний runbook для **обмеженого пілоту**. Доповнює, а не замінює
`docs/production-smoke-checklist.md` (детальний реліз-гейт) і `HOSTING.md`
(розгортання на Cloudflare). Усі перевірки на **staging лише синтетичними
даними**: ніколи не вводьте справжні ПІБ, телефон, діагноз, зображення чи опис;
не надсилайте реальних повідомлень; не змінюйте продакшн-дані.

> **Без заяв про відповідність.** Цей runbook — операційна готовність, а не
> підтвердження HIPAA/GDPR/ISO чи вимог МОЗ. Регуляторну відповідність
> підтверджують окремо з відповідальними за захист даних установи.

Орієнтири середовища: Cloudflare Workers + D1 (SQLite), єдина продакшн-база
`radiologyos` (`wrangler.cloudflare.toml`), міграції Drizzle у `drizzle/`,
реєстр застосованих міграцій — таблиця `d1_migrations`. Мультитенантність — за
`organization_id` із серверної сесії (`requireOrgContext`).

## 0. Передумови staging (одноразово)

Продакшн і staging **не можна** ділити одну базу. Створіть окреме середовище:

1. Створіть окрему D1: `npx wrangler d1 create radiologyos-staging`.
2. Скопіюйте шаблон `wrangler.staging.example.toml` → `wrangler.staging.toml` і
   замініть `REPLACE_WITH_STAGING_D1_ID` (та `REPLACE_WITH_STAGING_R2_BUCKET`,
   `REPLACE_WITH_STAGING_HOSTNAME`) на свої staging-значення. Продакшн
   `database_id`/домен у шаблон **не** скопійовано навмисно. Міграційний скрипт
   `apply-d1-migrations-remote.sh` **зупиниться**, доки плейсхолдер id не
   замінено (fail-closed).
3. Секрети staging (Telegram-токени тощо) — лише тестові, у Cloudflare secrets
   або БД `organization_integration_settings`, **не** в Git.
4. **Звичайний шлях — через workflow, не вручну.** Міграції на staging застосовує
   автоматично `staging.yml` (після налаштування Environment `staging` і запуску
   workflow — див. §0b). Окремо застосовувати їх вручну **не потрібно**.

   *Ручний fallback* (локальний/ad-hoc прогін, коли workflow недоступний або
   потрібно застосувати міграції поза ним):
   `bash scripts/apply-d1-migrations-remote.sh radiologyos-staging wrangler.staging.toml drizzle`.

Як у workflow, так і в ручному fallback виконавець `apply-d1-migrations-remote.sh`
**fail-closed** перевіряє конфіг і зупиняється (до будь-якого звернення до D1),
якщо: (а) `database_id` лишився плейсхолдером; (б) обрана база (1-й аргумент) не
збігається з `database_name` у конфігу; (в) **не**-продакшн конфіг указує на
**продакшн** `database_id` (напр. staging-конфіг із prod-ID). Продакшн-ID
зчитується з `wrangler.cloudflare.toml`, не захардкоджений.

> Якщо окремого staging ще немає — це **передумова пілоту**, а не блокер коду:
> виконайте кроки 1–4 перед рештою runbook. Нижче всі команди показані для
> `--config wrangler.staging.toml`; для перевірки прод-стану використовуйте
> read-only команди з розділів 1 і 5 проти продакшн-конфігу.

## 0b. Автоматизація через GitHub Actions

Staging автоматизовано окремими workflow-ами (production workflow `deploy.yml`
**не змінювався** й не запускається ними):

- **`ci.yml`** (тригер: кожен PR і push у `main`) — наявні перевірки (lint, tsc,
  build, тести, production-gate) **плюс** застосування **всіх** D1-міграцій до
  свіжої локальної синтетичної бази (`scripts/apply-d1-migrations-local.mjs`);
  SHA релізу й звіт міграцій зберігаються як summary + артефакт.
- **`staging.yml`** (тригер: push у `main` після злиття, а також `workflow_dispatch`)
  — **preflight** (`scripts/staging-preflight.mjs`) до будь-якого звернення до
  Cloudflare доводить, що staging D1 id / R2 bucket / hostname **не** збігаються з
  production (значення production читаються з `wrangler.cloudflare.toml`, не
  захардкоджені; hostname нормалізується; креденшели не читаються; fail-closed на
  збіг, відсутні чи плейсхолдерні значення). Далі рендерить `wrangler.staging.toml`
  з прикладу + значень оточення, застосовує міграції до staging (fail-closed
  guards), деплоїть **лише** з `wrangler.staging.toml`, робить health check
  розгорнутого staging і безпечний in-process E2E (пацієнт→дослідження→опис,
  ролі, ізоляція, і **обробку** Telegram-вебхука через тестовий секрет — це
  перевіряє парсинг/ідемпотентність/RBAC, **а не** фактичну доставку через Bot
  API; зовнішню доставку підтверджують вручну, §4Б). Summary + артефакт.
  **Інертний**, доки `vars.STAGING_ENABLED != 'true'`.
- **`staging-restore-rehearsal.yml`** (тригер: лише `workflow_dispatch` із
  підтвердженням `REHEARSE`) — створює **тимчасову** staging-базу, застосовує
  міграції, засіває синтетику, робить Time Travel bookmark → мутацію →
  відновлення → перевірку, і **завжди** (`always()`) видаляє **лише** створену
  ним тимчасову базу. Відмовляє, якщо ціль — реальне середовище чи продакшн id.

### Одноразове налаштування командою (GitHub → Environment `staging`)

Нічого з цього не комітиться; значення задає команда у своєму акаунті. Поки
їх немає — staging-workflow-и інертні (не падають, не шумлять).

**Variables** (Environment `staging`):

| Назва | Призначення |
|---|---|
| `STAGING_ENABLED` | `true`, щоб увімкнути staging-workflow-и (інакше вони пропускаються) |
| `STAGING_D1_DATABASE_ID` | id вашої staging-D1 (`radiologyos-staging`); **не** продакшн-id |
| `STAGING_R2_BUCKET` | імʼя приватного staging R2-бакета |
| `STAGING_HOSTNAME` | staging-домен (напр. `staging.example`) — **не** продакшн-домен |

**Secrets** (Environment `staging`, мінімальні права):

| Назва | Призначення |
|---|---|
| `CLOUDFLARE_API_TOKEN` | токен з правами лише на staging-ресурси (D1 edit, Workers deploy, R2 read) |
| `CLOUDFLARE_ACCOUNT_ID` | id Cloudflare-акаунту |
| `STAGING_E2E_STAFF_COOKIE` | *(необов'язково)* cookie **синтетичної** staff-сесії для браузерного E2E; без нього E2E чесно пропускається |

Cloudflare-ресурси (створює команда): staging-D1 `radiologyos-staging`,
приватний staging R2-бакет, staging-домен/маршрут. Рекомендовано ввімкнути
**required reviewers** на Environment `staging`, щоб deploy проходив людське
підтвердження.

## 1. Версія та застосовані міграції

**Версія коду (SHA):** реліз розгортається з `main`; збережіть SHA з логів
Actions. Список розгорнутих версій Worker:

```bash
npx wrangler deployments list --config wrangler.staging.toml
```

**Застосовані міграції vs код.** Локальний набір міграцій:

```bash
ls drizzle/*.sql | wc -l          # кількість міграцій у коді
ls drizzle/*.sql | tail -1        # остання міграція (нині 0128_study_region_contrast.sql)
```

Застосовані на базі (read-only):

```bash
npx wrangler d1 execute radiologyos-staging --remote --config wrangler.staging.toml --json \
  --command "SELECT name FROM d1_migrations ORDER BY id;"
```

Кількість рядків `d1_migrations` має дорівнювати кількості `drizzle/*.sql`, а
остання назва — збігатися. Деплой-скрипт `apply-d1-migrations-remote.sh` сам
блокує завершення, якщо локальна міграція не записана як застосована.

**Схема без читання даних пацієнтів** (перевірка нових колонок цього релізу):

```bash
npx wrangler d1 execute radiologyos-staging --remote --config wrangler.staging.toml --json \
  --command "SELECT name FROM pragma_table_info('bookings') WHERE name IN ('anatomical_regions','contrast_method');"
```

## 2. Резервне копіювання та відновлення копії на staging

**Бекап продакшну — D1 Time Travel** (на стороні Cloudflare, увімкнено). Перед
кожним деплоєм скрипт друкує recovery bookmark — зберігайте його з SHA релізу:

```bash
npx wrangler d1 time-travel info radiologyos --config wrangler.cloudflare.toml
```

Нижче — **дві різні** репетиції відновлення. Вони перевіряють різне; у звіті
фіксуйте окремо, яку саме пройдено. Обидві — **лише синтетичні дані**; реальні
записи пацієнтів із продакшну на staging не переносьте (це рознесло б PII у
середовище з іншим контролем доступу).

### 2A. Репетиція відновлення з синтетичного дампа (export/import) — ручна

Перевіряє, що **логічний дамп** staging відновлюється в чисту базу й застосунок
стартує проти відновленої схеми. Не використовує Time Travel.

1. Експортуйте **staging** (синтетичний) дамп у захищене сховище:
   `npx wrangler d1 export radiologyos-staging --config wrangler.staging.toml --output staging-dump.sql`
   (зберігайте лише зашифровано; ніколи не як публічний CI-артефакт).
2. Відновіть у чисту staging-базу імпортом цього дампа й переконайтесь, що
   застосунок стартує проти відновленої схеми.

### 2B. Репетиція D1 Time Travel restore (автоматизований workflow)

Перевіряє саме **механізм D1 Time Travel** (bookmark → мутація → restore →
перевірка) на окремій **тимчасовій** базі, яку workflow створює й видаляє сам.
Запуск: Actions → **Staging D1 restore rehearsal** → `workflow_dispatch` із
підтвердженням `REHEARSE` (`staging-restore-rehearsal.yml`). Основну staging-базу
й продакшн він **не** чіпає; перевіряє ціль і ніколи не приймає продакшн
`database_id`; cleanup тимчасової бази — через `always()`.

> **Продакшн** відновлюють лише через D1 Time Travel до збереженого bookmark
> (§2, бекап вище) за процедурою Cloudflare, з явним підтвердженням цілі
> (розділ 5). 2A/2B — це staging-репетиції, не продакшн-відновлення.

> Якщо політика установи дозволяє відновлювати реальну копію на staging —
> лише коли staging має еквівалентний контроль доступу й це погоджено з
> відповідальними за захист даних. За замовчуванням пілот працює з синтетикою.

## 3. Авторизація та ізоляція організацій

**Авторизація (серверна, не лише сховані кнопки).**

- Персонал: вхід потребує активного членства (`memberships.active=1`) і валідного
  PBKDF2-пароля. Деплой-скрипт блокує реліз без захищеного активного
  адміністратора.
- Ролі: предикати в `lib/staff-auth.ts` (`canManageBookings`, `canManageProtocols`,
  `canSignProtocols` — лише `radiologist`, `canViewPatientRegistry` тощо). Усі
  маршрути `/api/staff/*` перевіряють роль **після** `requireOrgContext`.
- Стан системи (лише системний адмін): `GET /api/staff/system/health`.

Ручна перевірка на staging (двома синтетичними ролями):

1. Реєстратор **не** може підписати протокол (підпис — лише лікар-рентгенолог).
2. Реєстратор **не** може редагувати підписаний протокол (вміст незмінний —
   БД-тригер `protocols_signed_content_immutable`).
3. Роль без доступу до `/staff/protocols` отримує захищений екран, а не дані.

**Ізоляція організацій.** Усі запити скоуповані `organization_id` із сесії.
Перевірка двома синтетичними організаціями A і B:

1. Сесія персоналу/пацієнта org A намагається прочитати/змінити
   заявку/пацієнта/протокол/дашборд org B за прямим id.
2. Очікувано: `404`/`403`, **ніколи** не дані іншої організації.

Регресійне покриття у коді (запускаються в `npm test`):
`tests/dashboard-tenant-isolation.behavior.test.mjs`,
`tests/bookings-tenant-hardening.behavior.test.mjs`,
`tests/patient-cross-tenant-direct-id.behavior.test.mjs`,
`tests/imaging-tenant.behavior.test.mjs` та інші `*tenant*`.

> Крос-тенантне читання чи запис — **негайна умова відкату** (розділ 5).

## 4. Основні сценарії (staging, синтетика)

Детальний синтетичний journey — `docs/production-smoke-checklist.md` §3–§5.
Пілотний мінімум, що має пройти end-to-end:

**А. Пацієнт → дослідження → опис → підписання/видача**

1. `/staff/dashboard` → **«Нове дослідження»** або `/staff/patients` →
   створити синтетичного пацієнта (ПІБ `TEST PILOT <sha>`, тестовий телефон,
   стать), за потреби — анатомічна ділянка + контрастування.
2. Створити walk-in дослідження (`/staff/protocols` → «+ Нове дослідження») або
   запланувати на `/staff/intake`; переконатися, що воно зʼявилось у черзі
   описів.
3. Відкрити дослідження, заповнити структурований опис/висновок, **зберегти
   чернетку**.
4. Лікарем-рентгенологом перевести `draft → ready → signed`; переконатися, що
   після підпису вміст незмінний.
5. Видати (`signed → issued`); у журналі аудиту `/staff/audit` події показані
   людськими мітками (зокрема **«Підписано протокол»**).
6. Друк/PDF опису показує анатомічну ділянку й контрастування, якщо заповнені.

**Б. Telegram-заявка — ручна перевірка зовнішньої інтеграції (лише синтетично)**

> **Що саме перевіряє цей крок.** Автоматизований E2E (у `staging.yml`) ганяє
> вебхук із **тестовим секретом** — він перевіряє лише **обробку вебхука**
> (парсинг, ідемпотентність, RBAC, чесний статус) і **не** підтверджує
> фактичну доставку через Telegram Bot API. Ось цей ручний крок із **тестовим
> ботом** — єдине, що перевіряє саме **зовнішню інтеграцію** (реальний виклик
> Bot API зі збереженим токеном). Обидва — синтетичні; реальним контактам не
> шлемо.

1. У `/staff/settings` збережіть **тестовий** `telegram_bot_token` і
   `telegram_webhook_secret` (бот і чат, що належать команді; не реальний
   пацієнт). Див. `docs/telegram-intake.md`.
2. Напишіть боту синтетичний вільний текст → заявка має зʼявитися в черзі
   «📨 Вхідні заявки» на `/staff/protocols` (ідемпотентно за `update_id`).
3. Візьміть у роботу, створіть дослідження із заявки (авто-звʼязок), надішліть
   підтвердження — **чесний статус**: без токена `sent:false` з причиною, не
   фальшиве «надіслано». У повідомленні — **мінімум** даних, без діагнозу/
   зображень/опису.
4. Без збереженого токена система показує «очікує налаштування»/помилку, а не
   успіх. **Ніколи** не шліть реальним контактам під час пілоту.

## 5. Виявлення помилок після деплою та відкат

**Виявлення.**

- CI-гейт зелений (Validate RadiologyOS + CodeQL) — передумова деплою.
- Логи Worker у реальному часі: `npx wrangler tail --config wrangler.staging.toml`.
- Стан системи: `GET /api/staff/system/health` (системний адмін) — БД, bookings,
  payments, PACS/MWL.
- Пройти §3 (public/security) і §4 (синтетичний journey + ізоляція) смоук-чеку.

**Умови відкату** (повний перелік — смоук-чек §7): крос-тенантний доступ;
публічне кешування приватних відповідей; клієнт може підмінити суму/дублювати
платіж; відсутні міграції або код не сходиться зі схемою; регрес прав на
протоколи; стійкі 5xx на канонічному сайті/букінгу/критичному API.

**Процедура відкату** (смоук-чек §8):

1. Зупинити операційне використання ураженого потоку.
2. Якщо збій **лише в коді** — передеплоїти останній відомо-робочий SHA.
3. Якщо міграція пошкодила схему/дані або старий код не працює з новою схемою —
   відновити через **D1 Time Travel** до bookmark, збереженого перед деплоєм
   (розділ 2), за процедурою Cloudflare з підтвердженням цілі.
4. Після відкату — повторити §3 і перевірку ізоляції (§3 цього runbook).
5. Відкрити блокуючий issue: SHA релізу, порушений інваріант, дію відкату, чи
   застосовано D1-відновлення. **Без даних пацієнтів у GitHub.**

- [ ] Автоматичний staging-прогін: `staging.yml` запущено, preflight пройдено, summary + артефакт перевірено.
- [ ] Версія: SHA релізу збережено; `d1_migrations` збігається з `drizzle/*.sql` (нині 128, остання `0128`).
- [ ] Схема нового релізу перевірена без читання рядків пацієнтів.
- [ ] Time Travel bookmark збережено перед деплоєм (з SHA).
- [ ] **Репетиція 2A** (export/import синтетичного дампа): дамп staging відновлено в чисту базу, застосунок стартує; реальні дані не переносили.
