# ADR 0001. Мультитенантність RadiologyOS

- Статус: прийнято
- Дата: 2026-07-29
- Контекст задає майстер-документ `RadiologyOS_structure_and_master_prompt.md`

## Контекст

RadiologyOS еволюціонує з операційної системи одного відділення променевої
діагностики у мультитенантний SaaS-конструктор для медичних організацій.
Єдина кодова база має обслуговувати кілька організацій (профілі Hospital
Radiology, Private CT, Dental, Outpatient Clinic) без форків. Перший і
пріоритетний еталон — відділення променевої діагностики Чернігівського
військового госпіталю.

Головна вимога — **tenant isolation**: дані однієї організації не повинні бути
доступні іншій за жодних обставин.

## Рішення

1. **Модель.** Вводимо організаційні сутності: `organizations`,
   `organization_profiles`, `branches`, `departments`, `memberships`
   (див. `db/schema.ts`). Профіль (`organization_profiles.profile_type` +
   `settings_json`/`feature_flags_json`) визначає поведінку організації.

2. **Ключ tenant у бізнес-даних.** Кожна бізнес-таблиця отримує
   `organization_id`. Для філіальних сутностей далі додаватимуться `branch_id`
   та `department_id`.

3. **Джерело `organizationId` — лише серверна сесія.** Контекст організації
   виводиться з перевіреної сесії персоналу через членство
   (`lib/tenant.ts` → `requireOrgContext`). `organizationId` **ніколи** не
   приймається з тіла запиту чи параметрів клієнта.

4. **Tenant-aware доступ до даних.** Вибірки й мутації бізнес-даних проходять
   через `lib/tenant-repo.ts`, де кожен запит явно фільтрує
   `organization_id = ?`. Крос-організаційний доступ покривається тестами
   (`tests/tenant-foundation.test.mjs`).

5. **Ролі та права — deny-by-default.** Канонічний перелік ролей у
   `ORG_ROLES`; поточний персонал використовує підмножину. Невідома роль не
   отримує прав. Матриця прав на рівні БД — окремий наступний крок.

## Стратегія міграції (тільки додаткові, без руйнувань)

Згідно з майстер-документом, застосовуємо лише additive versioned міграції
(`drizzle/0015_tenant_foundation.sql`):

1. створити організаційні таблиці;
2. створити початковий tenant (`slug: chernihiv-military-hospital-radiology`);
3. додати `organization_id` до бізнес-таблиць;
4. backfill існуючих рядків до початкової організації;
5. додати tenant-aware індекси;
6. поступово переводити код на нові сутності (цей та наступні PR);
7. **тільки після перевірки** — посилювати обмеження.

Кроки 3-4 реалізовано як `ADD COLUMN organization_id integer NOT NULL DEFAULT 1`:
існуючі й нові рядки безпечно належать початковій організації, доки код не
почне передавати контекст явно. Це навмисно **не руйнівна** зміна; жорсткіше
обмеження (прибрати DEFAULT, зовнішні ключі) відкладено до кроку 7 за окремим
погодженням.

## Наслідки

- Публічний сайт, онлайн-запис, кабінети пацієнта й персоналу, наявні API,
  міграції, тести й CI продовжують працювати без змін.
- З'являється фундамент для профілів організацій і feature flags.
- Наступні PR переводять конкретні домени (state machine досліджень, реєстр
  досліджень тощо) на tenant-aware доступ і додають `branch_id`/`department_id`
  там, де це потрібно.
