# On-prem (radiology-next) — інваріанти та патерни для портування

Короткий tech spec: що з `legacy-app` (cold-standby) має бути **відтворено** на
основному on-prem-бекенді. Не копія коду — перелік інваріантів і моделей.

## 1. Безпечне автозбереження чернетки = оптимістичне блокування + незмінність підпису

- **Оптимістичне блокування.** Клієнт шле `baseVersion`; будь-яка зміна `draft`/
  `ready` піднімає версію рівно на +1; розбіжність `baseVersion` ≠ поточної →
  **409** (захист від втрати чужих правок). Debounce автозбереження ~1 с.
- **Історія ревізій — append-only похідна проєкція, а не окремий запис застосунку.**
  На кожен крок версії БД-тригер створює знімок у `protocol_revisions`; UPDATE/
  DELETE ревізії заборонені; крок версії мусить бути +1; знімок мусить **точно**
  відповідати поточному документу. Наслідок: **коалесценцію ревізій робити НЕ можна**
  (зламає цілісність історії підпису). Оптимізація запису — лише «нічого не писати,
  коли вміст не змінився» (без приросту версії та ревізії) + автозбереження не пише
  в аудит.
- **4 рівні незмінності підписаного протоколу:** (1) RBAC `canManageProtocols`/
  `canSignProtocols`; (2) гейт дозволених переходів (`draft→draft|ready`,
  `ready→ready|signed`) → 409; (3) незмінність вмісту підписаного (БД-тригер);
  (4) `issued` — суто адміністративний стан поверх незмінного підписаного (перевірка
  тотожності клінічного документа).
- **Умовні переходи — через `UPDATE … RETURNING`**, не через `changes === 1`:
  тригери-проєкції роздувають `meta.changes` (на PostgreSQL — аналогічно стерегтися).

## 2. Планувальник ТО — forward-looking подання над `equipment_maintenance`

- Чиста проєкція поверх наявних рядків — **без нового API та міграції**.
- Бакети за `dueDate` відносно сьогодні: `overdue(<0)` / `today(0)` / `week(1..7)` /
  `month(8..30)` / `later(>30)`; порожні опущено; усередині — за зростанням строку.
- У планувальник входять лише **активні датовані** записи (`open`/`in_progress` зі
  строком); `done`/`cancelled`/без дати — виключені. KPI «найближчі N днів» =
  кількість активних датованих у `[0..N]`.
- `daysUntil` — цілодобова UTC-арифметика над `YYYY-MM-DD`; некоректна дата → `null`.
