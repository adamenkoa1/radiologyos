# UI/UX-аудит сторінки — правила проєкту RadiologyOS

Цей документ — **робочий playbook** для професійного аудиту та вдосконалення
будь-якої сторінки RadiologyOS. Він діє **разом із** `AGENTS.md` (канонічні
правила) і **не скасовує** його обмежень. За конфлікту — пріоритет у `AGENTS.md`.

## Команда-тригер

> «Проведи повний UI/UX-аудит цієї сторінки за правилами проєкту, внеси
> покращення та перевір результат.»

Коли користувач надсилає URL, маршрут, назву сторінки, скриншот або код і
просить аудит (або вживає тригер вище) — автоматично виконай процес нижче.

## Ролі

Працюй одночасно як Principal Product Designer, Senior UI/UX Designer, Senior
Frontend Engineer, UX Researcher, Accessibility Expert і QA Engineer. Мета —
сучасний, естетичний, інтуїтивний, швидкий, адаптивний, професійний продукт
рівня провідних SaaS (орієнтири: Linear, Stripe, Apple, Vercel, Notion — як
принципи, **не** копіювати буквально; зберігати власну систему RadiologyOS).

## 1. Перед змінами — зрозумій систему

1. Прочитай (якщо ще не читав цієї сесії): `AGENTS.md`, `docs/design-system.md`,
   `docs/styles.md` (реальні токени й CSS-зони в `app/styles/`), `docs/components.md`,
   `docs/pages.md`.
2. Знайди реальну реалізацію сторінки (`app/staff/<...>/page.tsx` або
   `public/site/...`) і її стилі (відповідний файл у `app/styles/`).
3. Визнач наявні токени (`--ws-*`), спільні компоненти, патерни (напр.
   `role="tab"`/`aria-selected` вже використовує `/staff/imaging`) — **повторно
   використовуй їх**, не вигадуй окремий стиль для сторінки.

## 2. Повний аудит (напрями)

- **UI / Visual:** композиція, ієрархія, типографіка, палітра/контраст, відступи,
  сітки, вирівнювання; кнопки, картки, таблиці, форми, меню; іконографіка;
  відсутність візуального шуму.
- **UX / Usability:** логічність структури, інтуїтивність навігації, мінімум
  кліків, зручність вводу, інформаційна ієрархія, ефективність сценаріїв; чіткі
  стани **завантаження / помилки / успіху / порожнечі**; запобігання помилковим діям.
- **Responsive:** Desktop 1280–1920, Tablet 768–1024, Mobile 320–430; без
  горизонтального переповнення; зручне сенсорне керування; читабельність.
- **Accessibility (WCAG 2.2 AA):** семантична структура, клавіатурна навігація,
  **видимий фокус (§2.4.7)**, контраст ≥4.5:1 (великий текст ≥3:1), коректні
  `label`/`aria`, озвучення станів і помилок (`role="alert"`/`role="status"`).
- **Technical:** якість і повторне використання компонентів, продуктивність,
  відсутність дублювання, коректна поведінка інтерактивних елементів.

Не лише шукай дефекти — пропонуй, що **спростити, прибрати, об'єднати, переробити**,
як зменшити кількість дій і підвищити зрозумілість. Оцінюй з позиції реального
користувача (пацієнт / медперсонал / адміністратор), з урахуванням медичної
специфіки. Не додавай функції чи декор без обґрунтованої користі.

## 3. Межі автономності (ОБОВ'ЯЗКОВО)

**Можна самостійно** (косметичні, композиційні, локальні UX/a11y-покращення):
- верстка, відступи, типографіка, стани, мікровзаємодії у межах **наявних
  токенів і спільних компонентів**;
- ARIA, фокус, семантика, контраст, повідомлення станів;
- локальні CSS-класи сторінки та її розмітка **без зміни даних, що показуються**.

**Спершу узгодь із власником** (окреме рішення):
- бізнес-логіка, маршрути, API, схема БД, авторизація, права доступу, платежі;
- зміни **глобальної дизайн-системи** або спільних компонентів (оціни вплив на
  інші сторінки — напр. тач-таргети/щільність по всьому shell);
- видалення наявних функцій або важливої інформації;
- зміна погодженої термінології (див. `AGENTS.md`).

Не використовуй фіктивні дані як реальні. Зберігай стабільність, безпеку й
функціональність. Якщо доступний лише скриншот — зроби візуальний аудит, але
**не заявляй про зміни коду**.

## 4. Перевірка результату (ОБОВ'ЯЗКОВО, чесно)

Після змін запусти доступні перевірки й познач, що саме виконано:
- `npx tsc --noEmit` — чисто;
- `npm run lint` — 0 errors (baseline-warnings лишаються);
- `npm test` (`build` + node-тести; guard `dead-css` підтверджує, що класи/селектори
  не зламані);
- додай короткий **source-inspection тест** на ключове покращення (патерн репозиторію);
- перевір адаптив/стани на рівні коду (наявні `@media`, токени, темна тема).

**Обмеження браузера:** сторінки `/staff/*` за автентифікацією + живим D1 —
піксельну перевірку в браузері на desktop/tablet/mobile зазвичай **виконати не
можна**; чесно це познач, не став «перевірено», якщо не робив. Публічні сторінки
(`/`, `/price`, кабінет) можна перевіряти в браузері (Playwright/Chromium наявні).

Не вважай завдання завершеним, доки не усунуті критичні/суттєві дефекти в межах
доступних інструментів.

## 5. Оцінювання (обґрунтовано, не завищено)

| Критерій | Макс |
|---|---|
| Візуальний дизайн | 20 |
| UX / зручність | 25 |
| Адаптивність | 15 |
| Доступність | 10 |
| Функціональність | 15 |
| Узгодженість дизайн-системи | 10 |
| Продуктивність | 5 |
| **Разом** | **100** |

Ціль — 95+/100, але оцінка має бути обґрунтованою. Якщо критерій не перевірено —
познач «неперевірено», а не вигадуй бал.

## 6. Фінальний звіт

Коротко й структуровано: **Сторінка** (маршрут) · **Оцінка до** · **Виявлені
проблеми** · **Виконані покращення** · **Додаткові пропозиції** (що потребує
узгодження) · **Оцінка після** · **Перевірки** (що виконано + обмеження) ·
**Змінені файли**. Без дрібних технічних деталей.

## 7. Процес доставки (як у цьому проєкті)

Одна функціональна задача — один PR; маленькі коміти. Розробка на designated-гілці
з `AGENTS.md`/системних інструкцій, повний цикл: CI зелений → squash-merge →
скид гілки на свіжий `main` → перевірка деплою. Оновити `docs/changelog.md`
(і `docs/lessons.md`, якщо з'явилося нове правило).

## 8. Постійне вдосконалення

Кожна наступна сторінка враховує вже прийняті рішення; не повторюй виправлених
помилок. Системну проблему виправляй на рівні спільного компонента/дизайн-системи
(попередньо узгодивши). Після всіх сторінок — готовність до загального аудиту
цілісності UX, навігації та візуальної системи.
