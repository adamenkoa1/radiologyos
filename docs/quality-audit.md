# RadiologyOS — матриця покриття аудиту якості

Персистентний облік системного аудиту (MASTER PROMPT 1 + 2). Мета — довести
**весь** продукт до єдиного стандарту якості під контролем, а не точково.
Цей файл продовжується між сесіями: перед роботою звір статуси тут, після
кожного модуля — онови рядок і додай PR.
## Актуальний зріз станом на 2026-10-29

Звірено з main після PR #706. Останні завершені зміни: Telegram intake queue #686; фільтри черги описів #687; стать пацієнта #688; структуровані ділянки/контраст #689; входи дашборду й audit label #690; staging/runbook/preflight #691–#696; автозбереження протоколу #701; задача після неявки #703; постійний план для агентів #704. Не трактувати їх як відкриті задачі без доказу дефекту.

CI і CodeQL для останнього baseline PR #705 пройшли (CI #2080, CodeQL #2006); перевірки PR #706 відстежуються окремо. Кодова база має 128 SQL-міграцій, остання відома — `0128_study_region_contrast.sql`. Кількість сторінок, API-маршрутів і тест-файлів нижче більше не фіксується приблизно: її треба переобчислювати під час відповідного інвентаризаційного кроку.

Візуальні позначки нижче відображають доказ у матриці, а не припущення. Старий локальний browser-block описаний станом на 2026-10-12 і потребує повторної перевірки, якщо середовище змінилося. Staging автоматизований, однак workflow може бути пропущений, доки staging не налаштований/увімкнений; не вважати його живий запуск виконаним без успішного run у Actions.



## Легенда статусів
- **не перевірено** — модуль ще не проходив цілеспрямований аудит;
- **перевіряється** — аудит у процесі (відкритий PR/гілка);
- **перевірено** — пройдено аудит, змін не потребує (зафіксовано, чому);
- **потребує виправлення** — знайдено дефект, виправлення ще не змерджено;
- **виправлено** — виправлення змерджено;
- **повторно перевірено** — після виправлення повторно пройдено весь чек-лист.

## Вимір аудиту (для кожного модуля)
Функціонал/сценарії · UI/UX · дублювання/мертвий код · a11y (WCAG 2.2 AA) ·
адаптивність · продуктивність · безпечні покращення · тести/регресії.

### Три окремі підперевірки (обовʼязкова вимога)
Кожен модуль фіксуємо за **трьома** незалежними підперевірками:
- **Технічна** — код, типи, lint, автотести, dead-code/dedup, a11y на рівні розмітки.
- **Функціональна** — сценарії, стани помилок/порожні, навігація, resilience (читанням логіки + behavior-тести).
- **Візуальна** — фактичний рендер у браузері під роллю на desktop/tablet/mobile зі скриншотами.

Сторінка **не** позначається «повністю перевірено», доки всі три не зелені.

### Візуальна перевірка staff-сторінок

Остання зафіксована перевірка локального browser-runtime була 2026-10-12; її
висновок про `ASSETS`/D1 є історичним і не повинен автоматично вважатися
актуальним. Перевірки з роллю й viewport мають окремий статус у рядках матриці:
автотести або припущення користувача не замінюють зафіксований screenshot/ручний
результат. Staging automation (#693–#696) додає можливий шлях перевірки через
staging та синтетичну staff-cookie, але запуск лишається пропущеним, доки
staging не налаштований/увімкнений. Відсутність такого запуску не блокує
незалежні кодові та read-only аудити.

Для локального середовища перед повторним висновком перевірити, чи виправлено
історичну проблему з `env.ASSETS.fetch`. Точну кількість міграцій, route-файлів
і тестів брати з актуального checkout/Actions, не з цього старого опису.

сторінкових PR). За AGENTS.md контракти API, права доступу, схема БД і платежі
змінюються **лише після погодження**, тож тут аудит зосереджений на:
безпеці tenant-ізоляції, коректності станів, обробці помилок — **на рівні
читання**, без зміни контрактів. Детальний per-route облік — наступний етап.

Індекс дедуплікації intake не унікальний — конкурентне дублювання лишається окремим відкритим питанням. |

Цільова підперевірка `/api/telegram/webhook` (#706): технічна — missing D1 fail-closed і відповідний behavior-тест; функціональна — секрет/tenant resolution, захоплення intake, повторна доставка та команди перевірені читанням і наявними behavior-тестами. Візуальна перевірка не застосовується до API. Залишковий ризик: наявний індекс `intake_requests_dedup_idx` не є UNIQUE, отже конкурентні однакові update_id теоретично можуть створити дубль; безпечна міграція потребує окремо оцінити вже наявні рядки.

Примітка: кількість тест-файлів тут навмисно не фіксується — дивись актуальний CI та переобчислюй із checkout під час інвентаризації. Автотести не замінюють цілеспрямований read-only огляд API.
