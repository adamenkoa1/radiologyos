## Легенда статусів
- **не перевірено** — модуль ще не проходив цілеспрямований аудит;
- **перевіряється** — аудит у процесі (відкритий PR/гілка);
- **перевірено** — пройдено аудит, змін не потребує (зафіксовано, чому);
- **потребує виправлення** — знайдено дефект, виправлення ще не змерджено;
- **виправлено** — виправлення змерджено;
- **повторно перевірено** — після виправлення повторно пройдено весь чек-лист.
- **перевірено частково** — цільову перевірку завершено, але лишився окремо задокументований ризик або неперевірена зовнішня інтеграція.
- **потребує рішення** — виявлена неоднозначність продуктового правила або рівня підтвердження особи; поведінку не змінювати без рішення власника.

## Вимір аудиту (для кожного модуля)
Функціонал/сценарії · UI/UX · дублювання/мертвий код · a11y (WCAG 2.2 AA) ·
адаптивність · продуктивність · безпечні покращення · тести/регресії.

### Три окремі підперевірки (обовʼязкова вимога)
Кожен модуль фіксуємо за **трьома** незалежними підперевірками:
- **Технічна** — код, типи, lint, автотести, dead-code/dedup, a11y на рівні розмітки.
- **Функціональна** — сценарії, стани помилок/порожні, навігація, resilience (читанням логіки + behavior-тести).
- **Візуальна** — фактичний рендер у браузері під роллю на desktop/tablet/mobile зі скриншотами.

Сторінка **не** позначається «повністю перевірено», доки всі три не зелені.

### Візуальна перевірка staff-сторінок

Остання зафіксована перевірка локального browser-runtime була 2026-10-12; її
висновок про `ASSETS`/D1 є історичним і не повинен автоматично вважатися
актуальним. Перевірки з роллю й viewport мають окремий статус у рядках матриці:
автотести або припущення користувача не замінюють зафіксований screenshot/ручний
результат. Staging automation (#693–#696) додає можливий шлях перевірки через
staging та синтетичну staff-cookie, але запуск лишається пропущеним, доки
staging не налаштований/увімкнений. Відсутність такого запуску не блокує
незалежні кодові та read-only аудити.

Для локального середовища перед повторним висновком перевірити, чи виправлено
історичну проблему з `env.ASSETS.fetch`. Точну кількість міграцій, route-файлів
і тестів брати з актуального checkout/Actions, не з цього старого опису.

## API — верхньорівневий статус (кількість маршрутів потребує перерахунку)
Окремі API-маршрути ще не пройшли повний per-route аудит. За AGENTS.md контракти API, права доступу, схема БД і платіжна поведінка змінюються лише в межах підтвердженого рішення власника. Переглянуті маршрути фіксуються нижче; невідомі зовнішні гарантії лишаються відкритими.

| Група | К-сть | Статус | Нотатки |
|---|---|---|---|
| Публічні (`/availability`, `/catalog`, `/site-*`, `/patient-*`, `/my-*`, `/liqpay-callback`, `/pay-link`, `/tariffs`) | не перераховано | перевірено частково | `/availability`, каталог і тарифи звірені з `effectiveServices`; patient access/payment initiation переглянуті; PR #714 має зелений CI/CodeQL, але зовнішній LiqPay retry після 503 не підтверджений. Решта public API не аудійована. |
| `/staff/*` операційні (`bookings`, `dashboard`, `studies`, `protocols*`, `result-deliveries`, `critical-findings`, `imaging*`) | не перераховано | не перевірено | Покриті behavior-тестами; аудит читанням |
| `/staff/*` BAS (`finance`, `business-documents`, `inventory*`, `reports*`, `cash-accounts`, `counterparties`, `supplier-payables`, `service-deliveries*`) | не перераховано | не перевірено | Immutable-реєстри; широке тестове покриття |
| `/staff/*` персонал/радіація (`personnel*`, `radiation-*`) | не перераховано | не перевірено | Append-only; захищені тригерами |
| `/staff/*` адмін/налаштування/інтеграції (`settings*`, `org`, `members`, `2fa`, `search`, `whatsapp*`, `telegram*`, `external-calendar`) | не перераховано | не перевірено | |
| Вебхуки (`/telegram/webhook`, `/whatsapp/webhook`) | не перераховано | перевірено частково | Telegram: відсутній D1 дає 503 (#706); intake-index не UNIQUE, атомарну дедуплікацію ще оцінити. WhatsApp: tenant-secret, D1=503, UNIQUE dedupe і погоджену телефонну видачу лише послуги/дати/часу перевірено; Green API live не тестувався. |

Цільова підперевірка `/api/telegram/webhook` (#706): технічна — missing D1 fail-closed і відповідний behavior-тест; функціональна — секрет/tenant resolution, захоплення intake, повторна доставка та команди перевірені читанням і наявними behavior-тестами. Візуальна перевірка не застосовується до API. Залишковий ризик: наявний індекс `intake_requests_dedup_idx` не є UNIQUE, отже конкурентні однакові update_id теоретично можуть створити дубль; безпечна міграція потребує окремо оцінити вже наявні рядки.

Цільова підперевірка `/api/whatsapp/webhook` (read-only, 2026-10-29): secret резолвиться до одного tenant; відсутній D1 повертає 503; вхідні `external_id` дедуплікуються UNIQUE-індексом; rate-limit scoped до tenant. Власник підтвердив вузький каналовий доступ команди «1 — Мої найближчі записи»: назва послуги, дата й час за вхідним WhatsApp-номером. Спільний номер означає спільну видимість цих записів; результати, протоколи й зображення недоступні через бот, OTP для кабінету не змінено. Візуальна перевірка не застосовується до API; зовнішня Green API доставка live не перевірялася.

Цільовий read-only огляд public service API (2026-10-29): `/availability` бере tenant із перевіреної staff-сесії або використовує public organization 1; `/catalog`, `/public-services` і `/tariffs` читають канонічний `effectiveServices`. Перетину tenant-ів у цих маршрутах не виявлено. Старий `/api/site-booking` атомарно резервує заявки й дедуплікує за idempotency key, але після збереження заявки збій `recordAnalyticsEvent` може повернути 500 до запуску сповіщень. Поточна публічна форма вже не викликає цей endpoint (вона передає заявку в месенджер), тому це задокументовано як legacy API edge case, а не як підтверджений дефект поточного шляху.

Цільовий огляд `/api/liqpay-callback` у PR #714: D1/config/booking/settlement failures повертають 503 + Retry-After, а replay settlement ідемпотентний. CI #2124 і CodeQL #2050 пройшли. Офіційна документація LiqPay описує callback та окремий status API, але не підтверджує повторну доставку після 503; live payment не виконувався. Треба визначити retry policy з провайдером або спроєктувати reconciliation через status API перед злиттям зміни.

Примітка: кількість тест-файлів тут навмисно не фіксується — дивись актуальний CI та переобчислюй із checkout під час інвентаризації. Автотести не замінюють цілеспрямований read-only огляд API.
