# RadiologyOS Modality Worklist bridge

RadiologyOS does not expose a DIMSE C-FIND listener directly to the public internet. Instead it exposes a narrow HTTPS feed for an on-premise bridge that is responsible for presenting the data to modalities as DICOM Modality Worklist (MWL) or the DICOMweb Modality Scheduled Procedure Step service.

## Security model

- Each organization has one independently rotatable bridge token.
- Only the SHA-256 hash of the token is stored in D1.
- The raw token is returned once, when an administrator creates or rotates it.
- The bridge sends the token only in `Authorization: Bearer <token>`.
- `organization_id` is never accepted from the bridge request; tenant ownership is derived from the token hash.
- The feed is `Cache-Control: no-store` and contains only fields required to construct a worklist item.
- Phone, email, comments, referrals, payment data, notes and protocol/report text are not returned.
- Disable or rotate the token immediately if the bridge host is replaced or a secret may have leaked.

Admin UI: `/staff/integrations/mwl`

Feed: `/api/integrations/mwl?from=YYYY-MM-DD&to=YYYY-MM-DD`

Optional filter: `modality=CT`, `modality=DX`, or `modality=RF`. A request may cover at most 31 days.

## Feed fields

Each item contains:

- `scheduledProcedureStepId` — stable RadiologyOS booking/study step code;
- `accessionNumber` — manually assigned imaging accession when present, otherwise the booking code;
- `patientId` — stable organization-scoped DICOM patient identifier generated by RadiologyOS;
- `patientName` and `patientBirthDate`;
- `modality` — `CT`, `DX`, or `RF`;
- `scheduledDate` and `scheduledTime`;
- `procedureDescription`, `serviceCode`, and `equipmentId`.

The bridge must not substitute its own patient demographics when a worklist row is present. It should use the RadiologyOS values so the acquired DICOM study carries the same accession/patient identity used for later PACS linking.

## Status selection

Only scheduled work is exposed: `scheduled`, `confirmed`, and `rescheduled`. Cancelled, no-show, completed and other non-scheduled states are excluded by the server query.

## Modality mapping

RadiologyOS maps CT equipment to `CT`, digital X-ray and chest fluorography to `DX`, and the barium fluoroscopy services 301–303 to `RF`. This mapping follows DICOM acquisition modality terminology used by the MWL Scheduled Procedure Step Modality attribute.

## Suggested on-premise topology

1. Run a small bridge service on a managed host inside the hospital/radiology network.
2. Store the RadiologyOS bridge token in that host's secret store, not in source code or command-line history.
3. Let the bridge poll the HTTPS feed for a narrow date window and keep only a short-lived local worklist cache.
4. Expose DIMSE MWL C-FIND or DICOMweb Modality Scheduled Procedure Step only on the internal modality network.
5. Map `equipmentId` to the actual local modality AE Title in the bridge configuration. RadiologyOS intentionally does not reuse the PACS AE Title as a modality station AE Title.
6. When images reach PACS, RadiologyOS can resolve the resulting study by the same Accession Number through the existing QIDO-RS auto-link workflow.

DICOM references: PS3.4 Annex K (Basic Worklist Management / Modality Worklist) and PS3.18 Chapter 14 (Modality Scheduled Procedure Step Service and Resources).
