# Lessons Learned

## 1. Публічний сайт і внутрішня система — різні контури

Публічний сайт призначений для пацієнтів.
Внутрішня система — для персоналу.
Вони можуть мати спільний дизайн, але різні вимоги до безпеки.

## 2. GitHub Pages не є медичною інформаційною системою

Не зберігати на ньому реальні:

- ПІБ;
- телефони;
- діагнози;
- направлення;
- протоколи;
- DICOM;
- медичні документи.

## 3. Одна заявка — один пацієнт

У заявці може бути кілька досліджень.
Не створювати дублікати пацієнта для кожної послуги.

## 4. Календар організовується за ресурсами

Основні ресурси:

- кабінет;
- апарат;
- модальність;
- персонал.

## 5. Погоджена структура ролей

Є:
- завідувач;
- старший рентгенлаборант;
- лікар-рентгенолог;
- лікар УЗД;
- рентгенлаборант;
- медична сестра;
- санітарка;
- реєстратор;
- інженер;
- системний адміністратор.

Немає ролі «старша медична сестра».

## 6. Пантомографія, не мамографія

Не додавати непогоджені модальності.

## 7. Сервер — другий етап

Етап 1:
- Web MVP;
- HTML/CSS/JS;
- тестові дані;
- UX-перевірка.

Етап 2:
- локальний сервер;
- PostgreSQL;
- API;
- Orthanc;
- DICOM;
- реальна авторизація;
- журнал дій;
- резервні копії.

## 8. Сенсорний інтерфейс не повинен залежати від hover

Кнопки й дії мають бути видимі на планшеті.

## 9. Оплата лише після підтвердження

Оплату доцільно показувати після перевірки запису, дати, послуги й суми реєстратором.

## 10. КТ із контрастом потребує окремого workflow

Обов'язково враховувати:
- креатинін;
- катетер;
- алергію;
- супутні ризики;
- рішення лікаря у невідкладних випадках.

## 11. Внутрішня система — це облікова система клініки, а не набір сторінок

Для господарської частини RadiologyOS базовим референсом є BAS Small Company.

Канонічна модель:

```text
Довідники → Документи → Проведення → Регістри → Звіти
```

Наслідки:
- гроші, борги, залишки, виробіток і завантаження не повинні жити як незалежні вручну редаговані підсумки;
- проведений документ не переписується непомітно — потрібне коригування/сторно;
- внутрішні екрани мають використовувати спільні форми журналу, довідника, документа, вибору та звіту;
- друковані форми є частиною ядра, шаблони версіонуються, а історичний друк має бути відтворюваним;
- медичні модулі (DICOM, протоколи, clinical workflow) накладаються поверх бізнесового ядра та додають суворіші правила доступу й незмінності.

## 12. Legacy-рухи не можна перетворювати на вигадані документи

Під час переходу старого ledger на BAS-подібні документи не робити backfill за евристиками. Якщо старий рух не мав документа-реєстратора, він залишається explicit `Legacy` з `documentId = null`.

Це краще, ніж помилково приписати реальний рух неправильному документу, пацієнту, партії або періоду. Усі нові господарські рухи після переходу повинні мати точний registrar.

## 13. Історична друкована форма не дорівнює повторному рендеру поточних даних

Після першого формування non-draft документа зберігається immutable snapshot конкретної версії шаблону і стану документа. Повторний друк має читати цей snapshot.

Зміна назви матеріалу, реквізитів довідника або нового шаблону не повинна тихо змінювати те, що вже було сформовано/надруковано раніше. Для доказовості snapshot має версію та hash і не допускає UPDATE/DELETE.

## 14. Публічний `pending` не є господарським фактом

Канонічна межа:

```text
BAS Small Company = бізнесове ядро.
RadiologyOS = BAS-подібне ядро + медичні модулі.
Публічний сайт = зовнішня вітрина і канал запису.
```

Публічний сайт може ініціювати booking або платіж, але `pending payment_transaction` — це технічний стан інтеграції, а не проведена оплата. Гроші з'являються в business-core тільки після trusted confirmation, який створює/проводить `payment` document і його register movements.

З цього випливає правило: public route не повинен напряму INSERT-ити `cash_movements`, `patient_settlement_movements`, `revenue` чи інші господарські регістри.

## 15. Технічний платіжний ledger і господарський registrar — різні речі

`payment_transactions` потрібен для provider reference, pending/paid/refunded status, callback idempotency і технічної звірки. Він не замінює BAS-документ.

Для нової оплати потрібен точний `payment_document_id`; для повернення — окремий `refund_document_id`. Встановлений link не можна обнулити або підмінити. Історичні paid/refunded transactions без links залишаються Legacy, а не отримують вигаданий документ заднім числом.

## 16. Повернення грошей не дорівнює сторнуванню доходу

Документ `refund` рухає:

- `cash` зі знаком мінус;
- `patient_settlements` зі знаком плюс.

Він не повинен автоматично сторнувати `revenue`, бо гроші можуть повертатися без скасування самого факту надання послуги. Якщо змінюється факт/обсяг наданої послуги, дохід коригується окремим service correction/storno document із простежуваним зв'язком із першоджерелом.

## 17. Автоматичні operational tasks мають одного authoritative owner

Якщо runner вважає свій candidate-set повним і автоматично закриває відкриті automation-task, яких більше немає серед кандидатів, нові автоматичні джерела не можна реалізовувати паралельним trigger/cron-процесом.

Клінічні handoff-задачі тому додаються до того самого authoritative candidate engine. Вони є похідним read-model від канонічного стану дослідження, використовують стабільний `automation_key`, оновлюють існуючу open task при зміні виконавця/строку і не копіюють ПІБ, діагноз або клінічний текст у title/details чи security audit.

## 18. Remote D1 migrations мають окремий parser-compatibility ризик

Міграція може успішно виконуватися стандартним SQLite/local test і все одно впасти під час `wrangler d1 migrations apply --remote`, якщо клієнтський SQL splitter некоректно розбирає line comments у багатостейтментному файлі.

Для migration, яка вже продемонструвала такий збій, не додавати звичайні `--` prose-коментарі всередину SQL-файлу; залишати лише технічні `--> statement-breakpoint`, а пояснення переносити в документацію/PR. Production gate має окремо перевіряти цю parser-sensitive умову до звернення до remote D1. Не послаблювати database guards і не позначати migration застосованою вручну для обходу помилки parser-а.
