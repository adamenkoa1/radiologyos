# RadiologyOS

Повноцінна система онлайн-запису відділення променевої діагностики Чернігівського військового госпіталю.

## Можливості

- публічний каталог із 38 послугами, цінами, внутрішніми кодами та відомими кодами eHealth;
- онлайн-запис для військових і цивільних пацієнтів;
- окремий розклад для КТ, цифрового рентгену та флюорографа;
- перевірка перетину записів з урахуванням тривалості процедури;
- блокування технічних вікон і простоїв обладнання;
- кабінет пацієнта для перевірки та скасування заявки;
- захищений кабінет персоналу зі статусами, перенесенням, нотатками та історією змін;
- операційний пульт відділення: зведені показники (розклад дня, виконання, протоколи, знімки, оплати, пацієнти) та дієві списки «що зробити зараз» із переходами в один клік;
- призначення лікаря-рентгенолога та рентгенолаборанта на кожне дослідження;
- фіксація фактичного виконання, кількості анатомічних ділянок і номера зовнішнього документа;
- облік фактичних дат готовності й видачі протоколів із окремими правами лікаря;
- конструктор протоколів зі структурованими шаблонами за модальностями (КТ, рентген, флюорографія), автопідбором шаблону, типовими формулюваннями норми, версійністю, статусами «чернетка → готовий → виданий» та друком/PDF;
- CRM пацієнтів: єдина картка за номером телефону з історією візитів, протоколів та оплат, профілем (ПІБ, рік народження, теги, нотатки, «не турбувати»), журналом комунікацій і сегментами (повторні, майбутні візити, очікують протокол, борг оплати);
- AI-асистент протоколів: детерміністична чернетка висновку й рекомендацій зі структурованих полів із підсвіткою відхилень від норми та врахуванням історії пацієнта; працює офлайн без ключів і має єдину точку підключення реального LLM;
- інтеграція DICOM/PACS: прив’язка дослідження до DICOM-студії (Accession, StudyInstanceUID), робочий список, запуск у зовнішньому переглядачі та автоматичне підтягування серій через DICOMweb (QIDO-RS) із конфігуруванням ендпойнта адміністратором;
- внутрішній облік суми до сплати, фактичної оплати та перевірки НСЗУ;
- конструктор звітів із фільтрами, вибором колонок і п’ятьма готовими шаблонами;
- справжній Excel-експорт без ПІБ і телефонів пацієнтів та журнал усіх експортів;
- ролі адміністратора, реєстратора, лікаря-рентгенолога й рентгенолаборанта;
- керування доступом працівників без зміни коду;
- серверна валідація, нормалізація українських номерів і обмеження частоти запитів.

## Архітектура

- Next.js 16 і React 19;
- Vinext та Cloudflare Workers;
- Cloudflare D1;
- Drizzle ORM і версійовані SQL-міграції;
- власна авторизація персоналу (email + пароль, сесії в D1, без зовнішніх провайдерів);
- захищені заголовки браузера, рольове розмежування доступу й журнал чутливих операцій.

Публічний сайт, запис, база заявок і кабінет персоналу працюють як одна система та використовують одну базу D1.

## Локальний запуск

Потрібен Node.js `>=22.13.0`.

```bash
npm run install:ci
npm run dev
```

Корисні команди:

```bash
npm run lint
npm exec tsc -- --noEmit --incremental false
npm run build
npm test
npm audit --omit=dev --audit-level=high
npm run db:generate
```

## База даних

Схема описана у `db/schema.ts`, а послідовні зміни зберігаються в `drizzle/`.
Початкова міграція створює заявки, а наступні додають предметну та операційну модель RadiologyOS:

- апарати та тривалість процедур;
- категорію пацієнта й тип направлення;
- нормалізований телефон;
- журнал подій і службові нотатки;
- персонал та ролі;
- технічні блокування обладнання;
- таблицю обмеження частоти запитів;
- протоколи досліджень;
- статуси оплати, фактичну сплачену суму та НСЗУ;
- призначених виконавців і фактичний час виконання;
- кількість анатомічних ділянок і номер зовнішнього документа;
- фактичні дати готовності та видачі протоколу;
- індекси для звітності за виконанням, обладнанням і виконавцями;
- журнал експорту звітів;
- одноразові ключі ідемпотентності запису та короткоживучі сесії пацієнтів;
- незмінні ревізії протоколів, фіксацію згоди й журнал доступу до медичних даних.

Серверні API не створюють таблиці під час звичайних запитів.

## Доступ персоналу

Персонал входить на сторінці `/staff/login` за робочим email і паролем. Сесія зберігається у `HttpOnly`, `Secure`, `SameSite=Strict` cookie на 12 годин, а в D1 — лише SHA-256-хеш токена. Паролі зберігаються як PBKDF2-HMAC-SHA-256 із 600 000 ітерацій і випадковою сіллю. Самореєстрація та публічне відновлення пароля вимкнені.

Активного адміністратора або стандартного пароля в міграціях немає. Перший обліковий запис створюється адміністратором інфраструктури безпосередньо в D1 за процедурою з `HOSTING.md`; усіх наступних працівників додає адміністратор на сторінці `/staff`.

Розподіл прав:

| Роль | Заявки | Виконання / знімки | Протоколи | Пацієнти й оплата | Звіти / експорт | Налаштування |
|---|---|---|---|---|---|---|
| Адміністратор | усі, керування | усі, керування | усі, керування | керування | перегляд і експорт | керування |
| Реєстратор | усі, керування | фіксація виконання | немає | реєстр і оплата | немає | немає |
| Лікар-рентгенолог | лише призначені | лише призначені | лише призначені | немає | немає | немає |
| Рентгенолаборант | лише призначені | лише призначені | немає | немає | немає | немає |

Готові шаблони звітів: реєстр досліджень, контроль протоколів, навантаження персоналу, навантаження обладнання та фінансовий реєстр. Період звіту визначається фактичною датою виконання, а для ще не виконаних записів — запланованою датою. ПІБ і телефони в Excel не включаються, але деталізовані реєстри містять дані про медичні послуги й мають зберігатися та передаватися лише захищеними каналами.

## Доступ пацієнта

Кабінет пацієнта вимагає повний номер телефону та код заявки. Після успішної перевірки сервер видає короткоживучу `HttpOnly`-сесію; номер телефону не зберігається у `localStorage`. Протокол доступний лише після статусу «виданий». Публічна форма не завантажує медичні файли: направлення потрібно передати персоналу погодженим захищеним каналом або принести на візит.

## Захист даних

Система зберігає лише дані, необхідні для організації запису. Заявки створюються атомарно з ключем ідемпотентності, згода фіксується з версією тексту, виданий протокол незмінний, а перегляд реєстру пацієнтів, протоколів, звітів та експортів журналюється.

Перед робочим використанням власник системи має:

- затвердити правову підставу й строк зберігання даних;
- перевірити вимоги установи до розміщення медичних даних у Cloudflare D1;
- обмежити доступ до проєкту та регулярно переглядати список персоналу;
- затвердити порядок резервного копіювання, видалення та реагування на інциденти.

Наявні поля оплати й НСЗУ є внутрішнім операційним обліком персоналу. Вони не списують кошти та не надсилають дані до ЕСОЗ. Інтеграції з оплатою, НСЗУ або зовнішньою МІС підключаються лише після вибору офіційного провайдера, договору та погодженої специфікації API.

## Зовнішні інтеграції

Вихідні HTTP-запити дозволені лише через HTTPS, без облікових даних у URL, без редиректів і без приватних/локальних адрес. У production задайте точний список дозволених хостів через змінну `OUTBOUND_ALLOWED_HOSTS` (через кому) для PACS, зовнішнього календаря, SMS та e-mail шлюзів. Telegram-повідомлення про нову заявку містить лише код і бажаний час — без ПІБ, телефону, категорії, назви дослідження чи коментаря пацієнта. Токен приватного календаря зберігається лише як хеш і показується адміністратору один раз під час створення.

## CI/CD

CI перевіряє ESLint, TypeScript, тести, production-збірку й відомі вразливості залежностей. CodeQL та Dependabot увімкнені окремими конфігураціями. GitHub Actions закріплені на конкретних commit SHA.

Production-деплой запускається лише вручну після вибору `DEPLOY`, проходить через GitHub Environment `production`, фіксує поточний D1 Time Travel bookmark, застосовує міграції за іменем бази та завершується smoke-тестом `https://radiologyos.tech/`. Деталі первинного налаштування й відновлення — у `HOSTING.md`.
