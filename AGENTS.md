# AGENTS.md — RadiologyOS

Цей файл є обов'язковою інструкцією для Codex, ChatGPT та інших AI-агентів, які змінюють код RadiologyOS.

## Канонічна архітектурна межа

```text
BAS Small Company = бізнесове ядро.
RadiologyOS = BAS-подібне ядро + медичні модулі.
Публічний сайт = зовнішня вітрина і канал запису.
```

Наслідки:

- господарські факти належать business-core і проходять `Довідник → Документ → Проведення → Регістр → Звіт`;
- медичний шар може бути підставою для бізнес-документа, але DICOM/PACS, протоколи, результати та клінічні revision lifecycle не перетворюються на бухгалтерські/господарські сутності;
- публічний сайт може прийняти заявку, показати каталог, ініціювати оплату та відкрити patient entry, але не є власником проведених господарських фактів і не пише напряму в бізнес-регістри;
- підтвердження зовнішнього платежу повинно входити в business-core через trusted server adapter і створити/провести канонічний документ, а не напряму змінити фінансові підсумки.

## Обов'язкові правила

- Основна мова інтерфейсу — українська.
- Поточний етап — Web MVP.
- Локальний сервер, PostgreSQL, Orthanc і DICOM — наступний етап.
- Не зберігати реальні медичні дані на GitHub Pages або в `localStorage`.
- Не додавати роль «старша медична сестра».
- Є роль «старший рентгенлаборант».
- Використовувати «пантомографія», не «мамографія».
- Погоджені модальності: КТ, рентгенографія, флюорографія, пантомографія, УЗД.
- Одна заявка належить одному пацієнту і може містити кілька досліджень.
- Календар організовується за кабінетами/обладнанням.
- Внутрішні сторінки повинні мати `noindex,nofollow`.
- AI не приймає клінічне рішення замість лікаря.
- Внутрішня система `/staff` є BAS Small Company-подібною операційною системою клініки; публічний сайт є окремою вітриною та intake-каналом.
- Публічний `pending` платіж або заявка не дорівнює проведеному господарському факту.
- Проведені господарські документи не можна тихо переписувати: зміни фактів виконуються через коригування/сторно та простежуваний зв'язок із першоджерелом.
- Підсумки на кшталт грошей, боргу, залишків, виробітку та навантаження походять із документів/рухів, а не з вручну редагованих агрегованих полів, якщо немає окремо задокументованої причини.
- Друковані форми є частиною ядра: шаблони версіонуються, а сформовані історичні форми мають бути відтворюваними з конкретного snapshot.
